Astryx × Local LLMs

Can a local model build with Astryx?

The same task given to four models running entirely on a laptop via LM Studio - across three runs. Run 1 was a simple flower-shop page. Run 2 was a demanding, production-grade 10-section marketing site with real imagery and a working light/dark theme toggle. Same build-gated harness; every linked page is unedited model output.

Built with @astryxdesign/core@0.3.0. API discovered through the @astryxdesign/cli. Metrics from LM Studio's native API.

Run 1

simple prompt · header · hero · 6 cards · about · visit

A single-viewport flower shop. The floor: can the model find the right components and build something that renders?

Exact prompt sent (Run 1)
Build a landing page for a flower shop called "Petal & Stem" as src/App.tsx.

Sections:
1. A header row (HStack) with the shop name (Heading) on the left and a cart indicator on the right: a Button labeled like "Cart (N)" whose N comes from useState and increments when any "Add to Cart" is clicked.
2. A hero: a centered Heading (use type="display-1" or level={1}), a warm one-line tagline (Text type="large"), and a primary Button "Shop Now".
3. Featured bouquets: a Grid (responsive, columns={{minWidth: 280}}) of 6 bouquet Cards. Use floral color variants (pink, green, yellow, purple, etc). Each card: bouquet name (Heading level={3}), a one-line description (Text type="supporting"), a price (Text weight="bold"), a Badge on some ("Bestseller" -> success, "Seasonal" -> warning), and an "Add to Cart" Button (size="sm", primary) wired to increment the cart.
4. About: a Heading and two short Text paragraphs about fresh, locally-sourced flowers.
5. Visit Us: a Card with address, hours, phone (each a Heading level={4} label + Text lines), and a standalone Link "Get Directions".
6. Footer: shop name (Heading) and a small tagline (Text type="supporting").

Use real bouquet names (Rose, Peony, Tulip, Sunflower, Orchid, Wildflower, etc). Constrain the page to a centered column around maxWidth 1100 using VStack + centering. Generous gaps between sections (gap={8} or {10}). Make it inviting and production-quality — but obey every Astryx rule (no div, no inline styles, spacing-scale numbers only).

Run 2

production spec · 10 sections · imagery · theme toggle · newsletter

A real launch site: app shell, hero, trust strip, product grid with photos, occasions, how-it-works, testimonials, a controlled newsletter input, and a working light/dark toggle - all wired with state. This is where model size and stamina show.

Exact prompt sent (Run 2)
Build a complete, production-ready marketing website for a boutique flower shop, "Petal & Stem," as a single src/App.tsx. This is a real launch site — every section fully built, real copy, working interactions, light/dark support. Take visual cues from Astryx's Product Gallery template (real imagery, app shell, generous whitespace, strong hierarchy).

Global chrome:
- App shell via <Layout height="fill" contentWidth={1200}>. LayoutHeader top bar: brand "Petal & Stem" (Heading) on the left; on the right a nav row of ghost Buttons (Shop, Occasions, About, Contact), a light/dark theme toggle, and a "Cart (N)" Button whose count comes from useState and increments on every Add to Cart. Main content in LayoutContent padding={6}. Site wrapped in <Theme theme={neutralTheme} mode={mode}>.

Sections, in order:
1. HERO — two-column Grid (columns={{minWidth: 340}}). Left: an eyebrow Badge ("Fresh daily · Locally grown"), a large Heading (type="display-1"), a compelling paragraph (Text type="large"), and two Buttons — primary "Shop the collection" with a trailing arrow Icon, and a ghost "How it works". Right: a hero image (Card padding={0} + AspectRatio ratio={4/3} + picsum image, seed "petal-hero").
2. TRUST STRIP — a row (Grid columns={4} or HStack, wrap) of 3-4 small stats or reassurances with Icons: e.g. "Same-day delivery", "7-day freshness guarantee", "Hand-tied by florists", "Carbon-neutral shipping".
3. FEATURED BOUQUETS — section Heading + supporting Text, then a Grid (columns={{minWidth: 300}}, gap={6}) of 6 bouquet cards. Each: image (Card padding={0} + AspectRatio ratio={1} + unique-seed picsum), name (Heading level={3}), a 2-line description (Text maxLines={2}, color secondary), a price (Text weight="bold"), a category/status Badge on some (Bestseller→success, Seasonal→warning, New→info), and an "Add to Cart" Button (size sm, primary) wired to the cart. Vary the six with real names (Rose, Peony, Tulip, Sunflower, Orchid, Wildflower...).
4. OCCASIONS — a Grid of 3-4 clickable-feeling category Cards (Birthday, Anniversary, Sympathy, Just Because), each with an image or color variant, a Heading, and a short line of Text.
5. HOW IT WORKS — 3 steps (Grid or HStack), each a numbered/icon step with a Heading and Text: choose → we hand-tie → same-day delivery.
6. TESTIMONIALS — 2-3 customer quote Cards (Text for the quote, a Heading/Text for the name + role), tastefully laid out.
7. NEWSLETTER — a muted Card band with a Heading, a line of Text, a controlled TextInput for email (state), and a primary "Subscribe" Button. Show it's interactive.
8. ABOUT — Heading + two paragraphs of real brand story about fresh, locally-sourced flowers and the studio's craft.
9. VISIT US — a Card with Address, Hours, Phone (each Heading level={4} + Text lines) and a standalone external Link "Get Directions".
10. FOOTER — via LayoutFooter or a footer band: brand Heading, a tagline (Text supporting), columns of Links (Shop / Company / Support), and a small copyright line.

Requirements: real, specific copy throughout (no placeholders); unique picsum seeds so images load; the cart, newsletter input, and theme toggle all genuinely work via useState; light and dark both look right (tokens only). Aim for something you'd be proud to ship to a real florist. Obey every Astryx rule (no raw layout divs, no inline styles except the one image-fill const, spacing-scale numbers only).

⚙ Gemma succeeds by a different route. The 7.5B Gemma could not build the 10-section page in one shot - it failed all five repair rounds, its output collapsing under the weight of a ~500-line file. So it got the same spec, a different method: task decomposition. A fixed, correct App shell owns the imports and state wiring (theme toggle, cart, newsletter); Gemma then wrote each of the 10 sections as a small, independent function, each build-checked on its own. It nailed all 10 sections on the first try (0 retries, 1 rule slip). The lesson isn't that small models can't use Astryx - it's that small models need the work broken down. The larger models held the whole page in their head; Gemma needed it in pieces.

Run 3

vision-in-the-loop · desktop 1280 + mobile 390 · screenshots fed back · 3 revise rounds

The models can see. After building the Run 2 site, each model is shown two real screenshots of its own output - a 1280×900 desktop capture and a 390×844 mobile capture - and asked to critique and revise its App.tsx toward production-ready and fully responsive. Build, re-shoot, feed both images back, repeat for three revision rounds. Every model was first verified to genuinely accept image input (all four correctly read a test image).

How the vision loop works (pipeline + per-round critique)
Vision check first: each model was sent a rendered PNG (white word on colored blocks) and asked to read it. All four - Gemma 4 e4b, Qwen 3.6, Muse Glimmer, Nemotron 3 Nano Omni - answered correctly (type=vlm). Ollama's capability listing had shown Gemma WITHOUT vision; that was wrong for the LM Studio VLM builds.

Loop (harness_r3_vision.py), per model:
  round 0  generate the Run 2 production site (same 10-section spec)
           -> astryx/vite build gate (+ undefined-refs check)
           -> screenshot at DESKTOP 1280x900 and MOBILE 390x844
              (cdp.mjs extended: `viewport W H [mobile]` => Emulation.setDeviceMetricsOverride;
               screenshot --full => captureBeyondViewport for full-page height)
  rounds 1..3  send BOTH images back with a critique instruction:
           "Here is your page on desktop (1280) and mobile (390). Critique it as a
            senior product designer, then return a fully revised src/App.tsx that is
            production-ready and fully responsive on BOTH viewports. Fix anything that
            looks cramped, misaligned, overflowing, or unbalanced - especially on mobile.
            Astryx rules still apply: no raw layout divs, no inline styles, spacing-scale
            numbers only, tokens only for color."
           -> rebuild, re-shoot desktop+mobile, feed back again.

Each linked page is the model's round-3 output, unedited.

What vision changed - and where it backfired. The clearest win was on Qwen: its round-0 mobile view had the trust strip and "how it works" still laid out in multiple columns, cramped at 390px. Shown the mobile screenshot, it revised to stack those into a single column - a fix it made because it saw the problem, not because it was told. Muse kept polishing each round, but its rule-slip count crept up (0, 0, 1, 3) as later edits added small violations. Nemotron is the cautionary tale: it started with the single best round-0 site (a complete florist page, 22 cards), but the vision loop regressed it catastrophically - at round 1 its revision built yet rendered blank (a runtime crash the build gate missed), and by round 3 it had rebuilt a generic lorem-ipsum placeholder ("Title 1…Title 10", brand name garbled to "Actory Shop"), losing the real copy, prices, testimonials, and 6 of 10 sections. It ended up the most technically responsive (clean single-column mobile, 0 rule slips) while being by far the worst design. The honest lesson: iterative self-revision is not universally beneficial - a less-steady model can talk itself into destroying good work.
⚙ The counter-move: decomposition as a guardrail. Gemma (7.5B - four times smaller than Nemotron) took the same vision loop but on a decomposed base: a fixed, correct App shell owns the imports, state, and layout, and the model revises each of the 10 sections independently, each build-checked in isolation. The result is the mirror image of Nemotron: Gemma kept the entire florist site intact through all three vision rounds (30 headings, 15 cards, real bouquets, prices, testimonials, newsletter, footer) and is fully responsive on mobile. The structure it couldn't hold in its head as one 500-line file, it held easily in ten small pieces - and vision could then safely polish each one without the whole thing unravelling. Its honest weakness: Gemma steadily leaks Tailwind classNames (34 by round 3) that Astryx simply ignores - real rule slips the larger models avoided. And its round-0 decomposition build initially rendered blank (a runtime bug); the vision loop recovered it by round 1. The takeaway across Nemotron and Gemma: for a small local model, how you *structure* the task matters more than raw capability - decomposition is what let the 7.5B model outlast the 30B one.
